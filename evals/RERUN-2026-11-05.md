# Re-run after the harness fixes — 2026-11-05

Machine: **Rio PC, RTX 3060 12 GB** (WSL2), Ollama 0.40.14, `qwen3.5:4b`, ~65 tok/s.
The original numbers in PROJECT_PLAN §9.1 came from the RTX 3070 box, so
compare *within* this file first, then against §9.1.

"main" = `a44a9b1` (before this branch). "fixed" = this branch. Same machine,
same problems, same seeds and configs. Uncertainty comes from `python -m lib.stats`, a
cluster bootstrap over problems. With 3–5 problems, every interval is wide.

## 003 quick — thinking with oracle (5 problems × N=2)

| harness | C3_NT | C3_T | C3_T − C3_NT |
|---|---|---|---|
| main | 70% [50–90] | **20% [0–60]** | −50 pp [−90, +0] |
| fixed (`6d27b9c`) | 70% [30–100] | 80% [40–100] | +10 pp [+0, +30] |
| fixed + comma-CALC (`3d60599`) | 90% [70–100] | 50% [20–80] | −40 pp [−70, −10] |

What this shows:

- **On main, the thinking condition was mostly measuring the `<think>` leak.**
  6 of main's 8 C3_T failures stopped as `final_answer` after **0 calculator
  calls**. The thinking ran into the 8192-token cap, and the harness found
  "FINAL_ANSWER" inside the reasoning text. Salvage then scored a stray
  number (`2.0`, `3.0 km/s`, `35786000`). None of the fixed-harness runs fail
  this way.
- **With the leak fixed, the sign of the thinking effect is not settled.**
  The two fixed rows run the same code on every C3_T path except
  comma-separated CALC lines, which appeared in one log. They still differ by
  30 pp on C3_T. That gap is run-to-run noise at N=2, so **neither +10 nor −40
  is a finding**. The old "thinking hurts single-structure problems by 22 pp"
  (§9.1) should be withdrawn, not replaced.
- **Thinking is still capped by `max_tokens: 8192` per turn.** In the last
  fixed run, 3 of the 5 C3_T failures had at least one turn cut off at exactly
  8192 completion tokens. The reasoning ended without an answer, and the run
  ended in `no_progress` or `max_tool_turns`. `num_ctx` is 16384, so there is room to raise
  `max_tokens` for `_T` conditions. Until then, C3_T measures "thinking that
  fits in 8k", not thinking.
- **Comma-separated CALC lines (`3d60599`).** On astro-028 the model wrote
  `CALC: r1, r2, r3`. The calculator rejected the tuple, and every
  resubmission used up one of the 8 allowed tool turns. After the fix,
  astro-028 C3_NT went from 0/2 to 2/2.
- **Context overflow is now visible.** In the `6d27b9c` run, astro-031
  C3_NT r1 hit `peak_context_tokens = 16384`, the full `num_ctx`. The model
  looped on a LaTeX "**CALC:**" line until the context filled. Ollama
  truncates silently, so before `peak_context_tokens` this case could not be
  told apart from an ordinary wrong answer.

## 008 quick — decomposition (3 hard problems × N=3, oracle cards in both arms)

| harness | mono | decomp | decomp − mono | tokens decomp/mono | plans parsed |
|---|---|---|---|---|---|
| main | 56% | **100%** | +44 pp | 0.37× | 100% |
| fixed | 67% | **100%** | +33 pp [+0, +67] | 0.40× | 100% |

| problem | mono (fixed) | decomp (fixed) |
|---|---|---|
| astro-014 | 33% | 100% |
| astro-028 | 100% | 100% |
| astro-031 | 67% | 100% |

- This is the first measurement of the **reworked** decomposition. In the
  rework, the model writes a plan of calculator expressions and the harness
  runs them deterministically, with no model call per leaf. It went
  **18/18 across both harnesses at ~0.4× the tokens**. The first 008 run
  (PROJECT_PLAN §9.1) had decomp at 11% and only 44% of plans parsed.
- The two harness versions agree because decomp barely touches the fixed
  code paths. The mono difference (56% vs 67%) is within noise.
- Only 3 problems: sign test p=0.50. This is the strongest effect in the
  project so far, and the next confirmation to buy: `make -C 008-decomposition run`
  (5 problems × N=5, ~2 h on the 3060).
